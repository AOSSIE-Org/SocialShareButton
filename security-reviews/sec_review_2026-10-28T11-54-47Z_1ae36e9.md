Trust boundary used for the library: every option a host page passes in
(`url`, `title`, `description`, `hashtags`, `via`, `platforms`, `theme`,
`buttonText`, `customClass`, `buttonColor`, `buttonHoverColor`,
`buttonStyle`, `modalPosition`), whether via the constructor, a framework
wrapper prop, or the `data-*` attributes read by the always-on auto-init,
may carry attacker-controlled content (user-generated content or the page
URL). Each was traced to `innerHTML`, `href`/`location`, `window.open`,
attribute and style sinks. `url`, `title`, `description`, `hashtags` and
`via` are always `encodeURIComponent`-encoded into fixed-origin share URLs
or assigned through `input.value`; `theme` and `customClass` reach
`className` as a property; `buttonColor`/`buttonHoverColor` reach CSSOM
style properties; `platforms` is filtered against a fixed lookup table.
Those paths are safe. `buttonText` and `modalPosition` are not (Finding 1).

For CI, workflows were checked for `${{ github.event.* }}` interpolation into
`run:`/`script:` blocks, `pull_request_target` checkouts of untrusted code,
npm-token exposure and repository pushes. `pull_request_target` workflows
(`sync-pr-labels.yml`, `label-merge-conflicts.yml`) never check out PR code
and read the PR body only through `context.payload` or `env:`; the release
workflow interpolates only a regex-validated semver string; the npm token is
scoped to the single `npm publish` step of a maintainer-gated, push-to-main
job. No workflow issue cleared the confidence threshold.

Excluded from review: `node_modules/`, `dist/`, build output, lockfiles,
binary assets (images, fonts, badges).

## Findings

### Finding 1: Unescaped `buttonText` and `modalPosition` interpolated into `innerHTML` (XSS, reachable via `data-*` auto-init) — `src/social-share-button.js:111`

- Severity: Medium
- Confidence: 0.85
- Category: xss
- Description: `createButton()` builds the share button with
  `button.innerHTML = \`...<span>${this.options.buttonText}</span>\``
  (`src/social-share-button.js:107-112`), and `createModal()` builds the modal
  with `modal.innerHTML = \`<div class="social-share-modal-content ${this.options.modalPosition}">...\``
  (`src/social-share-button.js:123-124`). Neither value is escaped or
  validated, so any HTML in `buttonText`, or a `"` followed by markup in
  `modalPosition`, is parsed as live DOM, including event-handler
  attributes that execute script. Both options are documented only as plain
  strings ("Button label text", "Modal position on screen" in
  `README.md:621,627`), so integrators have no reason to sanitize them. The
  React, Preact and Qwik wrappers (`src/social-share-button-react.jsx`,
  `src/social-share-button-preact.jsx`, `src/social-share-button-qwik.tsx`)
  pass the props straight through, which defeats the escaping React users
  normally rely on for string props.
  More importantly, the library unconditionally auto-initializes any element
  carrying `data-social-share`, both at load and for every node later added
  to the DOM via its `MutationObserver` (`src/social-share-button.js:900-1018`),
  and copies `data-button-text` and `data-modal-position` into these same
  options (`src/social-share-button.js:911,916`). This makes the library a
  script gadget: on any page that loads it, an attacker who can inject only
  inert HTML with `data-*` attributes (for example through an HTML
  sanitizer that allows data attributes, which DOMPurify does by default, or
  a Markdown/rich-text renderer that preserves them) can turn that into
  script execution. The landing page's own demo
  (`landing-page/src/components/demo/DemoLauncher.tsx:83,109`) passes a
  free-text input to `buttonText`, confirming the sink renders HTML, though
  there it is only self-XSS because the value is not URL-driven.
- Exploit Scenario: A forum, blog or comment system includes the library
  from npm/jsDelivr and renders user posts through a sanitizer that keeps
  `data-*` attributes. An attacker posts
  `<div data-social-share data-button-text="<img src=x onerror=...>"></div>`
  (or the same payload via `data-modal-position='x"><img src=x onerror=...>'`,
  where the quote stays inside the attribute value until the library's template).
  The sanitizer sees a harmless `div` with data attributes and lets it
  through. When the post is rendered, or inserted later via AJAX, the
  library's auto-init reads the attribute, assigns it through `innerHTML`,
  and the injected handler runs in the host site's origin for every viewer,
  allowing session-riding, credential phishing or account actions. The same
  happens if a host passes a user-supplied or URL-derived label to the
  `buttonText` option or prop directly.
- Recommendation: Stop interpolating option values into HTML strings. In
  `createButton()`, keep the static SVG markup, then create the label with
  `const span = document.createElement("span"); span.textContent = this.options.buttonText; button.appendChild(span);`.
  In `createModal()`, remove `${this.options.modalPosition}` from the
  template and instead call
  `modal.querySelector(".social-share-modal-content").classList.add(pos)`
  only when `pos` is in an allow-list (`["center", "top", "bottom"]`),
  falling back to `"center"`. Apply the same allow-list approach to
  `theme` and `buttonStyle` for defense in depth. Add regression tests in
  `tests/social-share-button.test.js` asserting that a `buttonText` or
  `data-button-text` / `data-modal-position` containing markup produces no
  extra elements.

## Notes

### Note 1: Analytics payload carries the full page URL to host-configured third-party adapters — `src/social-share-button.js:788`

- Category: design-tradeoff
- Observation: `_emit()` puts `url: this.options.url` and `title` into every
  event payload, dispatches it as a bubbling, `composed` DOM `social-share`
  event, and passes it to `onAnalytics` and every `analyticsPlugins`
  adapter. When the host does not set `url`, it defaults to
  `window.location.href` (`src/social-share-button.js:20`), so any query
  string or fragment (for example a reset or invite token in the address
  bar) is included. The built-in adapters in
  `src/social-share-analytics.js:133-241` forward this value to GA4,
  Mixpanel, Segment, Plausible and PostHog as `share_url` / `url`.
- Rationale: The library documents this as intended: it is
  "privacy by design" in that it never sends data itself, only emits events,
  and "the host website (not this library) is the data controller"
  (`src/social-share-analytics.js:10-17`, `src/social-share-button.js:717-732`,
  `AGENTS.md` "Privacy by design"). The payload schema, including `url`, is
  documented, and forwarding only happens when the host opts in by
  configuring an adapter (and can set `analytics: false` or pass an explicit
  `url`). Removing the field would contradict the documented schema, so
  this is recorded as a Note for integrators rather than a Finding.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed,
  or traced at runtime, so timing-dependent, load-dependent, or
  infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a
  calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety
  guardrails built into some models can cause a real vulnerability to be
  softened, generalized, or left out rather than reported in exploit-level
  detail, and training-data bias can make some vulnerability classes
  easier for a model to recognize than others. Treat this report as a
  floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A
  vulnerability tied to a very recently disclosed CVE or library advisory
  may not be recognized as such.

**Review-specific limitations**

- Third-party dependency and GitHub Action source code was not reviewed
  (`node_modules/`, `sugar-high`, `next-intl`, `lenis`, and actions such as
  `AndreasAugustin/actions-template-sync@v2`, `eps1lon/actions-label-merge-conflict@v3`,
  `treosh/lighthouse-ci-action`). Several actions are referenced by mutable
  tag rather than commit SHA (including `actions/setup-node@v4` in the npm
  publish job of `version-release.yml`); this was treated as a hardening gap
  with no concrete exploit path and not reported. The landing page's
  `CodeBlock` relies on `sugar-high`'s `highlight()` escaping its input before
  `dangerouslySetInnerHTML`; all inputs to it are static snippets or
  allow-listed demo config, so this was not a finding, but the library's
  escaping was not verified from source.
- Repository and organization settings that affect CI risk (default
  `GITHUB_TOKEN` permissions, which apply to `seo-audit.yml` because it
  declares no `permissions:` block; branch protection; environment
  protection for `github-pages`; the scope of the `NPMJS_TOKEN` and
  `EXTERNAL_LABELLER_TOKEN` secrets) were not visible and could not be
  evaluated.
- Lockfiles were excluded by instruction, so no dependency-version
  vulnerability check was performed.
- Exploit detail in Finding 1 uses a generic placeholder handler (`onerror=...`)
  rather than a working payload; nothing else was held back.
